# Цифровая копия ЛКП

Цифровая копия ЛКП — browser-only стенд для проверки сквозных сценариев Личного кабинета партнёра, Админ-панели и двух бухгалтерских контуров. Это модель, а не production-ЛКП и не источник продуктовой истины.

## Архитектура

Все четыре интерфейса работают с одними бизнес-объектами:

`ЛКП + Admin + 1С ПГ + 1С РР → browser business layer → browser storage layer → localStorage`

Единственное постоянное состояние хранится под ключом `lkp-digital-copy-state`. Текущая версия — `schemaVersion: 11`. UI не хранит независимые постоянные копии данных: изменения записываются общими операциями, подписчики перечитывают state, а событие `storage` синхронизирует другие вкладки того же origin.

Основные файлы:

- `public/lkp-demo-data.js` — канонический согласованный demo state;
- `public/lkp-browser-storage.js` — чтение, единая запись, CRUD, подписки, reset и последовательные миграции;
- `public/lkp-browser-business.js` — корзина, договоры, счета, оплаты, УПД, баланс и активации;
- `public/lkp-data.js` и `public/lkp.js` — адаптер и legacy UI ЛКП;
- `app/admin/` — Админ-панель;
- `app/accounting-panel.tsx`, `app/1cpg/`, `app/1crr/` — общая реализация двух технических симуляторов 1С.

## Интерфейсы и маршруты

- `/` — ЛКП;
- `/admin/` — Админ-панель;
- `/1cpg/` — 1С Пи Джи Групп;
- `/1crr/` — 1С РР-Электро.

Все маршруты статически экспортируются и учитывают `NEXT_PUBLIC_BASE_PATH`. Для GitHub Pages они доступны под `/lkp-digital-copy/`, `/lkp-digital-copy/admin/`, `/lkp-digital-copy/1cpg/` и `/lkp-digital-copy/1crr/`.

1С-интерфейсы являются техническими симуляторами, а не копиями дизайна настоящей 1С. Переходы между ЛКП, Admin и обоими контурами находятся в технических шапках; симуляторы 1С не добавлены в пользовательское меню ЛКП.

## Ролевая политика и demo-авторизация

Пользователи являются общими бизнес-объектами Партнёра и доступны в ЛКП и Admin через единый browser storage. Поддерживаются две роли: `Владелец` и `Менеджер`; поле `isAdmin: true` соответствует Владельцу. У Партнёра ровно один Владелец. В Admin роль задаётся флагом `Администратор`: назначение нового Администратора автоматически снимает этот флаг с прежнего Владельца.

Владелец управляет пользователями Партнёра, а Менеджер видит их список без действий управления. Новый Менеджер создаётся сразу доступным для входа и получает demo-пароль. Отдельных актуальных состояний и действий активации или блокировки пользователя нет: поле `locked` сохранено только для legacy/compatibility и не участвует в авторизации. Доступ прекращается через soft delete (`deleted: true`), при котором Email заменяется техническим, текущие сессии пользователя становятся недействительными, а запись остаётся видна в Admin с пометкой удаления. Email действующего пользователя меняется через Admin.

Владелец может добавлять контакты, Менеджер — только просматривать. Оба пользователя имеют одинаковый бизнес-доступ к организациям Партнёра, каталогу, заказам, лицензиям и другим общим данным.

Форма входа использует Email и пароль, обязательное согласие и demo-действие `Забыли пароль?`; пароль можно показать или скрыть. Auth-сессия каждой вкладки хранится отдельно в `sessionStorage`, поэтому вход и выход в одной вкладке не подменяют сессию другой. Последние успешно использованные Email и пароль запоминаются отдельно в `localStorage`, а обязательное согласие не сохраняется. Пользователь может изменить собственный пароль.

Стартовые demo credentials:

- Владелец: `owner@demo.aqsi.ru` / `Owner123!`;
- Менеджер: `manager@demo.aqsi.ru` / `Manager123!`.

## Layout ЛКП

На desktop sidebar закреплён, а вертикальная прокрутка остаётся только у рабочей области. На mobile интерфейс возвращается к адаптивному одноколоночному layout с раскрываемым меню и горизонтальной прокруткой широких таблиц.

## Общая модель данных

State содержит пользователей Партнёра, организации, контакты, продукцию, незавершённую корзину, оформленные корзины, заказы, договоры, документы, лицензии, активации, балансы, принятия редакций оферты, справочники и постоянные счётчики.

Один заказ относится к одной организации и одному вендору. Одна корзина может породить несколько заказов: позиции группируются по паре `Организация + Вендор`, при этом номер корзины общий, а номера заказов, счета, оплаты, статусы и документы независимы.

Типы заказов:

- `Покупка товара`;
- `Авансовый платеж`;
- `Активация лицензий`.

Товарные заказы Пи Джи Групп, все авансы и все активации относятся к контуру ПГ. Контур РР содержит только товарные заказы РР-Электро.

Статусы заказов: `Принят`, `Ожидание сборки`, `Готов к отгрузке`, `Отгружен`, `Отменен`. Статусы активаций: `В работе`, `Выполнена`, `Ошибка`.

## Договоры и доступность товара

Договор — самостоятельная сущность с номером, организацией, вендором, типом, условием оплаты, статусом и признаком активности. Заказ всегда хранит `contractId`; случайного fallback на первый договор нет.

В справочнике типов поддержаны только:

- `Договор поставки`;
- `Сублицензионный договор`.

Конкретные сублицензионные договоры различаются полем `paymentTerms`: `Предоплата 100%` используется для авансов, баланса и оплачиваемых с баланса активаций, а `Постоплата 5 дней` — для активации до оплаты без баланса.

Без выбора организации и для ООО «ЗОЛОТОЙ СТАНДАРТ» каталог показывает товары Пи Джи Групп и РР-Электро. Для ООО Бета доступны только товары Пи Джи Групп; товары РР-Электро скрыты.

Версия сублицензионного договора хранится в записи `Сублицензионный договор` справочника типов договоров. `offerAcceptances` хранит принятую организацией версию: изменение полей конкретного договора не требует повторного принятия, а повышение `contractVersion` типа требует.

## Счета, документы и оплаты

Каждый новый заказ автоматически и один раз получает документ `Счёт на оплату`. Нумерация независима и хранится в state: ПГ использует `ПГ-100`, `ПГ-101`, …; РР — `РР-100`, `РР-101`, … . Строка `invoiceNumber` синхронизирована с документом.

Документы заказа:

- `Счёт на оплату`;
- `УПД`.

Файлы формируются в браузере через `Blob` и download. Счёт и УПД скачиваются с расширением `.pdf`, MIME `application/pdf` и пустым демонстрационным содержимым. Текстовый файл лицензий содержит ключи выполненной активации, не считается документом заказа и скачивается через связанную активацию. Для предоплатного заказа активации ЛКП показывает номер счёта, но скрывает файл счёта; УПД доступна. Admin и 1С показывают оба документа. Для постоплатной активации файлы счёта и УПД доступны во всех интерфейсах.

Проведение оплаты товарного заказа в соответствующей 1С меняет `Принят → Ожидание сборки`. Admin может необязательно перевести такой заказ в `Готов к отгрузке`. Проведение УПД из 1С разрешено из `Ожидание сборки` и `Готов к отгрузке`, создаёт одну УПД и переводит заказ в `Отгружен`.

Admin не проводит оплату, не создаёт счёт и не проводит УПД. Он показывает общие данные и документы, а из бизнес-действий заказа оставляет только готовность к отгрузке и отмену. Заказ с проведённой УПД отменить нельзя: действие скрыто в Admin и дополнительно запрещено в business layer.

## Авансы, балансы и активации

Баланс относится к паре `Организация + сублицензионный договор с предоплатой`. Канонический demo-сценарий ООО «ЗОЛОТОЙ СТАНДАРТ»: поступление 10 000 ₽, списание 4 000 ₽ за выполненную активацию, доступный баланс 6 000 ₽.

Создание авансового заказа и счёта не меняет баланс. После действия `Сформировать заказ` ЛКП открывает карточку созданного авансового заказа. После действия `Провести поступление денег` в 1С ПГ заказ становится оплаченным, сумма один раз зачисляется на баланс, а статус заказа остаётся `Принят`.

Для предоплатной активации достаточность баланса проверяется до создания. После успешного завершения сумма списывается один раз, создаётся один заказ ПГ, автоматически формируются счёт и УПД, а заказ сразу имеет состояния `Оплачено` и `Отгружен`.

Для договора с отсрочкой баланс не создаётся и не используется. После успешной активации заказ ПГ получает счёт и УПД, имеет статус `Отгружен`, но заказ и активация остаются неоплаченными. Последующее проведение денег в 1С ПГ отмечает оплату у обоих объектов.

Создание счёта, УПД, проведение денег, зачисление и списание баланса, создание активационного заказа и файла лицензий защищены проверками идемпотентности.

На экране выбора организации для активации у ООО Бета вместо баланса показано `Постоплата 5 дней`. После перехода на страницу ввода серийных номеров эта подпись не отображается.

### Серийные номера и activation draft

Activation draft хранится постоянно в общем browser state отдельно для каждой организации. Он переживает F5, переходы по другим страницам ЛКП и возврат; сохраняются нормализованные 16-значные серийные номера, их порядок и выбранные подписки. Draft не очищается при render, refresh или navigation.

Серийные номера можно вводить по одному или загружать из TXT, по одному номеру в строке; доступно скачивание примера с пятью demo-СН, заканчивающимися на `1`, `3`, `5`, `7` и `9`. Один и тот же нормализованный 16-значный номер нельзя добавить повторно: дубли фильтруются и при ручном вводе, и при загрузке TXT. Последний добавленный номер показывается сверху. После появления хотя бы одного валидного СН над таблицей отображается `Вендор: Пэй Киоск`.

Header таблицы активации закреплён. Внутреннего вертикального scroll у таблицы нет: на desktop вертикально прокручивается только рабочая область, а на mobile таблица при необходимости прокручивается по горизонтали.

Для подписок выводятся даты `Текущая до` и `Новая до`, рассчитанные относительно текущей даты. Сроки имеют серую, красную, жёлтую или зелёную индикацию; срок более 180 дней показывается зелёным и дополнительно отмечается плашкой `180+`.

Левый главный checkbox строки агрегирует checkbox доступных подписок: без выбранных подписок он `unchecked`, при частичном выборе — `indeterminate` с минусом, при выборе всех — `checked`. Клик по нему выбирает или снимает все доступные подписки. Отдельного persistent `rowSelected` нет. Удалить можно только полностью выбранные строки; частично выбранные строки не удаляются.

После создания записи активации использованные серийные номера удаляются из draft независимо от результата `В работе`, `Выполнена` или `Ошибка`. Если использована только часть подготовленных номеров, остальные сохраняются вместе с выбранными подписками.

При создании лицензионного заказа одинаковая номенклатура агрегируется по ключу `licenseType + model + unitPriceCents`: несколько одинаковых позиций объединяются в одну строку заказа с суммарным `quantity` и суммой строки.

## Миграции и демоданные

Storage выполняет последовательные миграции старых состояний до v11. Миграция `5 → 6`:

- заменяет старое название статуса `Ожидает сборки` на `Ожидание сборки`;
- нормализует статус оплаты `Не оплачен` в `Не оплачено`;
- добавляет канонические полноценные договоры, не удаляя пользовательские записи;
- преобразует баланс организации в баланс организации и сублицензионного договора;
- добавляет бухгалтерский контур и договорные связи заказам и активациям;
- создаёт недостающие документы из существующих номеров счетов и выполненных активаций;
- добавляет документные связи, постоянные счётчики и признаки уже проведённых финансовых операций;
- сохраняет пользовательские организации, контакты, товары, корзины, заказы и активации и не создаёт повторные счета или УПД.

Миграция `6 → 7` добавляет `offerAcceptances`, убирает доступность товаров РР-Электро для ООО Бета и нормализует имена существующих счетов и УПД до расширения `.pdf`. Миграции `7 → 8 → 9` сводят промежуточные варианты сублицензионных типов к одному типу `Сублицензионный договор`, переносят различия в `paymentTerms` конкретных договоров и сохраняют максимальную версию типа. Миграция `9 → 10` добавляет persistent `activationDrafts` в общий state.

Миграция `10 → 11` добавляет ролевую модель пользователей: переводит state на v11, дополняет `nextIds` недостающим счётчиком `user` и добавляет канонических demo-пользователей, только если массива `users` ещё нет. Существующие пользователи и все остальные пользовательские бизнес-данные не заменяются; последовательная цепочка миграций сохраняет организации, контакты, товары, корзины, заказы, договоры, документы, лицензии, активации, балансы и принятые редакции оферты.

Действие `Восстановить демоданные` атомарно заменяет общий state каноническим v11-снимком и уведомляет все интерфейсы.

## Локальный запуск и проверки

Требуется Node.js 22 (`>=22.13.0 <23`).

```bash
npm install
npm run dev
```

Vite обычно открывает проект на `http://localhost:5173`. Проверки:

```bash
npm test
npm run typecheck
npm run lint
npm run build
git diff --check
```

Последний pre-release checkpoint: `npm test` — 36/36, `npm run typecheck` — PASS, `npm run lint` — PASS, `npm run build` — PASS, `git diff --check` — PASS.

Production-сборка полностью статическая и размещается в `dist/client`.

## Публикация и ограничения

GitHub Pages публикуется только из `main`: GitHub Actions при push в эту ветку выполняет тесты, typecheck, lint и статическую сборку, затем публикует сайт. Опубликованный адрес: `https://zaktekinc.github.io/lkp-digital-copy/`.

Localhost и GitHub Pages имеют разные origin и независимый `localStorage`. Данные не синхронизируются между браузерами, устройствами и origin. Backend, API, БД, server runtime, настоящий обмен с 1С, настоящий ФР-Крипто, отдельный UI ФР-Крипто, журнал событий и настоящий PDF-генератор отсутствуют.
